Log a usage scenario

Use this form to enter the details for a usage scenario for tracking purposes. Filling this in doesn't save anything yet. The next step opens a pre-filled GitHub issue for you to review and submit (you'll need access to the private QTS-Data repo).

* Required

Administrative information

Required

The ID for a particular team's use case, kept for follow-up. One use case can have several queries. Pick an existing ID or add a new one.

Day, month and year the query was run.

Optional

Unique ID for this query, usually the query PK from the Translator UI. Leave blank to auto-generate the next number.

Name of the UEIC facilitator for this use case.

Use-case description

Required

One sentence summarizing what the user wants to do.

When they consult this service, what are they primarily looking for?

One sentence describing precisely the output the user would like to have.

Optional

A keyword to tag the type of use case.

Before using the service, how clearly is their question defined?

What do they prefer the system to do?

In this use case, how significant are the consequences of an incorrect answer? What would errors mainly cost?

Specific sources end users may already have in mind for this use case.

Query info

Required

The input node or set of inputs, as entered (not normalized). Separate several with semicolons.

The output node or set of outputs, as entered (not normalized). Separate several with semicolons.

The Translator interface or tool where the query was run.

Optional

Biolink category(ies) of the inputs, separated by semicolons. If there's no matching Biolink category or you're unsure, use a simple one-word description.

Biolink category(ies) of the outputs, separated by semicolons. If there's no matching Biolink category or you're unsure, use a simple one-word description.

Biolink predicate(s) used, separated by semicolons. To include child predicates, write "children of biolink:…". If you're unsure, use a simple one-word description.

The type of reasoning the user wants to do (nodes and edges can be lists; edges are directed).

Outcome

Required

Did the query run successfully? Success is defined by the facilitator for each use case.

Optional

Nodes in the results that are of interest to the user.

The outcome wasn't fully successful, so these fields about what went wrong are shown too. Fill in whatever applies.

Nodes that currently show up in the results but must not.

A few words on what the user needs to complete the query.

The Translator level affected by the need or development.

Can the user get the expected outcome another way? Give the development stage, e.g. "in house" if a power user has their own version.

Link to a separate GitHub issue (e.g. in the dev team's repo) tracking a problem, bug or enhancement found in this query. Not this submission's own issue. Leave blank if none.

Opens a pre-filled issue on the private QTS-Data repo, where you review and submit it.
